# FetchNews 后续阶段计划

## 目标

在现有 Phase 00 到 Phase 06 的基础上，把剩余能力拆成更小、可执行、可验收的后续阶段，避免“真实外部接入”“智能能力增强”“协作治理”“生产化部署”混在同一阶段里推进。

## 阶段总览

| 阶段 | 名称 | 核心目标 | 依赖 |
| --- | --- | --- | --- |
| Phase 07 | 外部真实能力接入 | 接入真实 `wechat / x / telegram` 发布器，补强真实采集连接器 | 现有采集、草稿、发布任务、运维面板 |
| Phase 08 | 智能内容能力 | 引入真实 LLM provider、embedding 去重和向量召回 | Phase 03 到 Phase 06 的内容链路 |
| Phase 09 | 编辑协作治理 | 补齐版本 diff、编辑历史、人工干预、权限与审计 UI | 现有编辑工作台和鉴权基线 |
| Phase 10 | 生产化部署 | 完成数据库迁移策略、部署编排、监控告警和运行手册 | 现有 PostgreSQL、Alembic、ops 面板 |

## Phase 07：外部真实能力接入

### 目标

把当前内部可跑的抽象发布器和连接器，升级为可实际对接外部平台和真实来源的生产实现。

### 范围

- `wechat / x / telegram` 真实发布器
- 更稳定的真实采集连接器
- 凭证管理和限流处理
- 平台回调或轮询状态同步
- 失败重试与幂等发布保障

### 详细任务

1. 真实发布器接入
- 明确各平台 API / webhook / callback 能力边界
- 为每个平台建立独立适配器和错误分类
- 将 `provider_job_id`、外部返回 ID 和回调结果统一落库
- 补齐发布成功、部分失败、超时失败、重复提交等场景

2. 真实来源连接器增强
- 优先补强高价值来源：GitHub、arXiv、官方博客 RSS、Hugging Face、Papers with Code
- 为每类连接器补认证、分页、增量抓取和异常恢复
- 统一原始数据快照，确保可追溯

3. 调度和风控
- 引入平台级速率限制和重试策略
- 按来源和平台记录失败归因
- 对敏感操作增加审计和告警

### 验收标准

- 至少有 1 个真实发布平台可以从草稿生成到发布结果回写闭环跑通
- 至少有 3 类真实来源连接器可以稳定抓取并进入 `raw_items`
- 发布失败后可幂等重试，不产生重复发布记录
- ops 面板能看到平台成功率和失败归因

## Phase 08：智能内容能力

### 目标

把现有模板驱动的内容生产升级为“规则 + 模板 + LLM + 向量能力”混合驱动，提升聚类、摘要、栏目编排和平台变体质量。

### 范围

- 真实 LLM provider 接入
- `pgvector` / embedding 去重和召回
- 更强的故事聚类解释
- 更丰富的平台文案策略
- 周报 / 月报栏目配比的智能优化

### 详细任务

1. LLM provider 抽象
- 建立统一 provider 接口
- 支持摘要、改写、标题生成、栏目提要和平台文案生成
- 为失败回退到规则模板预留兜底逻辑

2. 向量能力
- 为标准化后的条目生成 embedding
- 引入相似度检索，辅助去重和聚类
- 建立 story 召回和补全能力，减少漏聚和误聚

3. 聚类与栏目策略优化
- 利用向量相似度和来源权重优化 story 排序
- 为周报 / 月报建立更稳定的栏目配额和轮转逻辑
- 将历史互动反馈进一步反哺到稿件结构和平台变体

4. 平台文案智能化
- 平台模板从“固定写法”升级为“模板 + LLM 改写”
- 针对微信、X、Telegram 形成差异化生成策略
- 保留人工覆盖和锁定能力

### 验收标准

- 能从真实 LLM provider 生成摘要或平台变体，并可回退到模板
- 能用 embedding 辅助识别相似条目或重复报道
- 能在 ops 或编辑页上解释某条 story 为什么被聚合到一起
- 平台文案策略可以按模板和历史反馈自动切换

## Phase 09：编辑协作治理

### 目标

把当前单用户编辑工作台扩展为可审计、可回滚、可对比、可协作的内容治理界面。

### 范围

- revision diff 可视化
- 编辑历史明细页
- 人工干预记录与回放
- 段落级锁定、栏目级局部重建
- 更完整的权限与审计 UI

### 详细任务

1. diff 和回滚增强
- 做块级 diff 可视化，而不是只显示计数
- 支持版本树和恢复说明
- 支持锁定块与人工块的明确标记

2. 编辑历史
- 提供独立的编辑历史明细页
- 显示谁在什么时间改了什么
- 显示重建范围、模板切换和局部重建参数

3. 协作治理
- 支持草稿/版本的只读、可编辑、已锁定状态
- 补齐更细粒度的操作审计
- 按角色控制可见字段和可操作动作

### 验收标准

- 任意一版文章都可以看到块级 diff、编辑动作和回滚路径
- 局部重建不会覆盖锁定块和非目标栏目
- 审计日志可以从稿件、版本和动作三条线追溯

## Phase 10：生产化部署

### 目标

把当前可本地运行的系统收敛成可持续部署、可监控、可迁移、可恢复的生产方案。

### 范围

- 数据库迁移和初始化规范
- 部署编排和环境变量治理
- 告警、监控和 Runbook
- 备份、恢复和故障演练
- 更完善的前端测试和 CI

### 详细任务

1. 数据库与迁移
- 统一 Alembic 作为唯一 schema 变更入口
- 补齐开发、测试、生产三套数据库初始化说明
- 明确哪些 SQL 需要人工执行，哪些由迁移接管

2. 部署和配置
- 收敛 Docker Compose、环境变量和本机 PostgreSQL 的边界
- 为生产部署提供最小可行配置
- 明确 Redis、PostgreSQL、worker、beat、web 的启动顺序

3. 监控和运维
- 为失败聚合、平台成功率、栏目势能和发布回写建立告警阈值
- 建立常见故障的 Runbook
- 建立重试与回退原则

4. 测试和 CI
- 稳定前端测试执行方式
- 让后端、前端构建和关键测试在 CI 中可稳定运行
- 为发布前检查建立强制验证

### 验收标准

- 新环境按文档可完成启动、迁移和验证
- 生产级告警和监控信息可直接在 ops 面板查看
- 故障恢复路径有清晰文档和可操作步骤
- 测试和构建可以稳定进入 CI

## 推荐推进顺序

1. Phase 07：先把真实外部能力接起来，形成真实闭环
2. Phase 08：再补智能能力，提升内容质量
3. Phase 09：继续强化编辑协作和治理能力
4. Phase 10：最后收敛到生产化部署与运维

## 备注

- 以上阶段不是一次性全部实现，而是未来迭代的执行清单。
- 每个阶段开始前，应先更新对应阶段文档，再拆分成更小的任务。
- 如果某个阶段新增数据库字段或表结构，必须同步更新迁移和文档。
